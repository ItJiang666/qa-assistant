# qa-assistant · 智能问答助手

> 上传你的文档，用大模型问它 —— **回答只依据你上传的资料，并给出处；**。

一个基于 RAG（检索增强生成）的知识库问答助手：文档切片 → 向量化入库 → 提问时检索相关片段 → 交给大模型生成**有出处**的回答。

支持**本地模型**与**云端模型**，
并可在界面上**运行时一键切换**。


## 四步快速开始

```bash
# 注：以下模型选择为建议使用，非必需
# 1) 拉模型（一次性，约 8.5 GB）
ollama pull qwen3.5:9b && ollama pull qwen3-embedding:4b

# 2) 生成项目专用的向量模型
ollama create qa-embed:4b -f deploy/ollama/Modelfile.qa-embed

# 3) 启动（Windows 双击 start.cmd；命令行见下）
java -jar qa-assistant-1.0.0-SNAPSHOT.jar

# 4) 打开浏览器
#    http://localhost:8080
```

或者直接双击 / 执行**一键启动脚本**，先自检再启动：

| 平台 | 命令 | 脚本会检查 |
|---|---|---|
| Windows | 双击 `start.cmd`（或 `start.cmd 8081` 换端口） | JDK 版本、程序包是否带前端、Ollama 是否在跑、`.env` 是否存在 |
| Linux / macOS | `./start.sh`（或 `./start.sh 8081`） | 同上 |

> **脚本刻意不自动拉模型。** 8.5 GB 的模型下载需要自行决定是否下载；
>
> 脚本默认端口 8080，可用 `start.cmd 8081` 指定别的端口。

**不需要**装 MySQL、不需要 Node、不需要 Maven、**主流程也不需要 Python** ——
默认使用内置 H2 文件库，数据落在 `%USERPROFILE%\.qa-assistant\`（Windows）或
`~/.qa-assistant/`（Linux/macOS）。想整体搬到别的盘：设环境变量 `QA_DATA_DIR=D:/qa-data`（改后需重启）。

> 唯一的例外是**扫描版 PDF 的文字识别**（可选功能）：需要本机有 Python。
> 不装的话该功能不可用并在界面上给出提示，**问答、上传、检索全都不受影响**。
> 详见下方「扫描版 PDF 的文字识别」与「前置条件」。

> **装了 Python** 让"扫描版 PDF 识别"这项功能可用，一条命令：
> **有 NVIDIA/AND 独显** → `enable-gpu.cmd`；
> **没有独显** → `enable-ocr.cmd`。
> 两者都会把 OCR 依赖**一并装齐**，不需要先跑 `requirements.txt`，
> 并且会**检测环境、选对源、装完自检**。详见下方「可选：启用 GPU 加速」。

## 前置条件：按需分档

**最小前置只有 JDK 17+。** 其余都是按需：

| 想要的用法 | 必须装什么 | 一次性下载量 |
|---|---|---|
| **A. 纯云端模式** | **JDK 17+** + 云端 API Key | ~180 MB |
| **B. 本地离线（不处理扫描件）** | JDK 17+ + **Ollama** + 两个模型 | 约 **9 GB**（Ollama ~700 MB + 模型 ~8.5 GB） |
| **C. 本地 + 要处理扫描版 PDF** | B 的全部 **+ Python 3.10+** + 四步安装（见下方专节） | 再加约 **35 MB** |

明细：

| 项 | 要求 | 什么时候需要 |
|---|---|---|
| JDK | **17 或更高** | **始终需要**。已在 17 与 25 上各跑过一次验收 |
| Ollama | 任意近期版本 | **仅本地模式**。走云端模式可以不装 |
| Python | 3.10 或更高 | **仅"扫描版 PDF 识别文字"这一项可选功能**。不装不影响问答、上传、检索 |
| Python 依赖 | `python -m pip install -r deploy\ocr\requirements.txt`（**必须先 `cd /d` 到程序目录**，见下方四步） | 同上（约 50 MB，含模型，**装完即离线可用**；装的时候需要联网）<br>会装三个包：`rapidocr` + `onnxruntime` + `pymupdf` |
| 显卡 | 建议独显 ≥ 8 GB 显存 | **仅本地模式**。无独显可用：`num-ctx` 自动降级，或直接走云端模式 |
| 云端 API Key | 见 .env修改| **仅云端模式**。本地模式零配置即可启动 |

**不需要**：MySQL（默认内置 H2 文件库）、Node（发布包已含构建好的前端）、
Maven（发布包已含构建好的 jar）、GPU（云端模式下）。

### 硬件：推荐配置

按需选择：

| 场景 | 推荐配置 | 说明                                          |
|---|---|---------------------------------------------|
| **纯云端模式** | 任意办公机 | 只要 JDK 17 + 网络，**可以不需要独显**。推理在云端，本地只负责检索和界面 |
| **本地模式·最低可用** | 4 核 CPU / 8 GB 内存 / 无独显 | 能跑，但模型运行由CPU处理。`num-ctx` 会自动降级适配            |
| **本地模式·推荐** | 8 核以上 CPU / 32 GB 内存 / **独显 ≥ 12 GB 显存** | 本机就在这一档。12 GB 是能同时装下助手模型和向量模型的舒适线           |
| **扫描版 PDF 识别** | 在上一档基础上 + 8 GB 空闲磁盘 | OCR 走 CPU，不占显存。一本 50 页的扫描件约 2–3 分钟          |

两个模型加起来约占 **9 GB 显存**（助手 6.6 GB + 向量 2.5 GB），外加 KV cache，
所以 12 GB 是能两个都常驻、来回切换不重载的档位。
>  功能采用模块化设计 —— **只使用云端模式不需要下载Ollama**，
> 如果不需要使用OCR扫描则不需要安装Python环境。

`qa.local.num-ctx` 默认为 **`auto`**：启动时读 `nvidia-smi` 的显存总量，
≥11 GB 用 16384、≥7 GB 用 8192、探不到（无独显/非 N 卡）用保守的 4096 在日志里显示

## 扫描版 PDF 与图片的文字识别（可选）

扫描件、手机拍的纸质文件、微信收到的扫描 PDF，以及**直接丢进来的图片**
（jpg / jpeg / png / webp / bmp）—— 这类文件的**文字是图片、没有文字层**。

**上传后会自己识别一次**，识别完状态标签变成黄绿色的**「待确认」**，
点那一行的「查看识别结果」，核对无误后点确认才入库。识别全程在本机完成。

**两件事是分开的**：解析失败与有没有装 OCR 依赖**无关** —— 扫描件和图片本来就解析不出文字，
装了依赖它照样显示"失败"。依赖只决定**失败之后能不能救回来**（自动识别能不能跑起来）。
没装依赖时自动识别会失败，原因那一列会写清楚，装好之后点「识别文字」即可补救。

### 装依赖：

> 这一步**需要联网**（从 PyPI 下载，约 35 MB）。装完之后识别全程离线，模型随包下发。
> 不需要 Ollama，不需要显卡 —— OCR 走 CPU。

**第 1 步：确认 Python 可用。** 打开新的命令行窗口（`Win+R` 输入 `cmd`），执行：

```cmd
python --version
```

应显示 `Python 3.1x.x`。**如果提示"不是内部或外部命令"**，说明装 Python 时没勾
"Add python.exe to PATH"，重装一次并勾上（或改用 `py -3 --version` 试试）。

**第 2 步：进入你解压出来的程序目录。** 这一步不能省 —— 下面的路径是**相对路径**，
必须在程序目录里执行，否则会报 `Could not open requirements file`。

```cmd
cd /d D:\qa-assistant
```

把 `D:\qa-assistant` 换成你自己的解压路径。如果解压路径在C盘，`cd /d` 里的 `/d` 可以省略：但如果需要切换盘符时必须加它。
不确定当前在哪，先执行 `dir`，能看到 `start.cmd` 和 `deploy` 文件夹就对了。

**第 3 步：安装依赖。**

```cmd
python -m pip install -r deploy\ocr\requirements.txt
```

用 `python -m pip` 而不是直接敲 `pip` —— 前者不依赖 PATH 配置，更不容易出问题。

**第 4 步：自检。** 没报错、打印出下面引号内的两行内容就行了：

```cmd
python -c "import sys, rapidocr, onnxruntime, pymupdf; print('OCR 依赖就绪'); print(sys.executable)"
```
安装完依赖后，**关闭服务并重新启动**，即可生效。


### 装完之后

1. 上传扫描件 → 状态显示"失败"，原因里写明可用「识别文字」
2. 点该行的 **「识别文字」** —— 约 **1.3 秒/页**（100 页约 2 分钟；**装了 GPU 可到 0.5 秒/页**，见下方「可选：启用 GPU 加速」）
3. 弹出**确认对话框**：显示页数、有字页数、**内嵌插图统计**、平均置信度、识别文本预览
4. **核对后点「确认入库」** —— 才会真正分块入库；点「放弃」则文档不受任何影响

### 两条识别路径：页面上的字 + 插图里的字

识别不是只把每页当一张图扫一遍，而是分两路：

| 路径 | 管什么 | 结果 |
|---|---|---|
| **整页渲染**（主） | 页面上所有看得见的文字，**包括插图里的** | 绝大多数情况 —— 实测 200 DPI 下，页面里插图上的字也能读出来 |
| **逐张插图**（补充） | 单独抽出页面内的图片、放大后再识别 | 插图上字很小、整页渲染放大倍数不够时 |

第二路不是每次都产生内容：如果插图里的字**已经**被整页渲染读到了，这部分会被
**自动去重丢弃** —— 避免同一段内容出现两遍，其中一遍还可能带错字
（实测逐图放大会引入 `! d p`、全角 `２00` 这类伪影）。

所以确认对话框里"内嵌插图"那一栏要看懂：

- **未发现需要单独识别的插图** —— 正常。图标、logo、分隔线这类小图会被过滤掉
- **发现 N 张（其文字已包含在页面识别结果中）** —— 也正常，说明整页那一路已经读到了
- **发现 N 张，其中 M 张读出了额外文字** —— 图片那一路**补到了整页漏掉的内容**

三条设计取舍：

- **必须人工确认**：识别结果**不会自动入库**，要你点「确认入库」才生效 ——
  因为 OCR 扫描可能有错字，而错的文本一旦入库会被检索、被引用、被当成依据。
- **入库后会标注来源**：文档的"失败原因"列会写"正文来自本机 OCR 识别（rapidocr 3.x），
  非原件文字层" —— 你有权知道检索到的是原件原文还是识别的近似文本。
- **扫描功能非万能**：手写体、印章、竖排、多栏排版基本不可用；
  真实拍照件（倾斜、阴影、褶皱）的准确率明显低于印刷体，**数字与编号尤其要核对**。

> 识别引擎是 [RapidOCR](https://github.com/RapidAI/RapidOCR)（ONNX Runtime + PP-OCR 模型，
> 模型随 pip 包下发、**不需要运行时下载**），拆页用 PyMuPDF。选它们就是为了"离线可用"。

### 可选：启用 GPU 加速

不装也能用，只是慢一些。同一份 38 页扫描件实测：

| | 耗时 | 每页 |
|---|---|---|
| CPU | 65.3 s | 1.72 s |
| **GPU（RTX 5070）** | **20.2 s** | **0.53 s** |

准确率零损失：逐页相似度 99.96%，38 页里 33 页输出完全一致。

#### 一条命令启用

| 平台 | 命令 |
|---|---|
| Windows | 双击 `enable-gpu.cmd`，或在 cmd 里执行 `enable-gpu.cmd` |
| Linux / WSL | `bash enable-gpu.sh` |

>  在 **PowerShell** 里必须写成 `.\enable-gpu.cmd`。PowerShell 默认不从当前目录执行命令，
> 直接敲文件名会报「无法识别为 cmdlet、函数、脚本文件或可运行程序的名称」——看着像文件不存在，
> 其实是执行策略。

脚本做五件事：

1. 找到可用的 Python（≥ 3.10，会跳过 Microsoft Store 的假 `python3`）
2. 打印显卡型号、驱动版本、算力
3. **门槛检查**：无独显 / 算力低于 7.5（Turing） / 驱动低于 580 —— 任一不满足直接报错退出
4. 从官方源安装 OCR 基线与 CUDA 13 运行库（约 1.5 GB）
5. **验证**：用 CUDA 跑一次推理，输出必须与 CPU 一致才算成功

第 5 步是关键。只检查「CUDA 执行器在不在列表里」是不够的 —— 实测存在
「执行器注册了、动态库加载了、会话也建起来了，但一跑推理就失败」的情况，
那种机器上浅层自检会报成功，而真实 OCR 一个字都认不出来。

#### 门槛：什么样的机器能用

| 检查项 | 要求 |
|---|---|
| 显卡 | NVIDIA 独显，算力 **≥ 7.5**（Turing 及以后：GTX 16 系 / RTX 20 系起） |
| 驱动 | **≥ 580**（CUDA 13 的要求） |

GTX 10 系及更早（含 1060 / 1080Ti）不能用：驱动侧的 CUDA 支持已停止。
驱动不够时**没有降级方案**，升级驱动即可，不用换显卡。

#### 参数

| 参数 | 作用 |
|---|---|
| `--check` | 只打印检测结果，不安装 |
| `--verify` | 只验证当前是否可用，不安装 |
| `--cpu` | 跳过 GPU，只装 CPU 版基线 |
| `--help` | 用法 |

需要代理时先设环境变量 `HTTPS_PROXY`，pip 会自己读取。

#### 装完怎么确认

1. 重启应用
2. 上传一份**扫描版 PDF**
3. 看日志 `%USERPROFILE%\.qa-assistant\logs\qa-assistant.log`（Linux 为 `~/.qa-assistant/logs/`），
   出现「启用 GPU」即生效

也可以随时跑 `enable-gpu.cmd --verify`（或 `bash enable-gpu.sh --verify`）复查。

#### 手工安装

不想用脚本时：

```cmd
python -m pip install onnxruntime-gpu==1.31.0 nvidia-cudnn-cu13~=9.0 nvidia-cublas ^
  nvidia-cuda-nvrtc~=13.0 nvidia-cufft~=12.0 nvidia-curand~=10.0 nvidia-cuda-runtime~=13.0 nvidia-nvjitlink ^
  rapidocr pymupdf
```

> `onnxruntime-gpu` 只是推理后端，真正认字的是 `rapidocr`、拆页的是 `pymupdf`，
> 这两个不会被 GPU 包带进来。另外**不要用 `onnxruntime-gpu[cudnn]` 这种 extras** ——
> 实测它一个 CUDA 运行库都不会装进来。

装完同样要验证：

```cmd
python deploy\ocr\qa_ocr.py --check --use-gpu on
```

#### 两个常见问题

**① 机器上有多套 Python 时，确认应用用的是哪一个。**
应用按 PATH 顺序找 `python3` / `python`，可能挑中一个没装依赖的解释器 ——
表现是「装好了应用却说缺依赖」或「装了 GPU 还在用 CPU」。
解决办法是在启动 jar 的目录下建 `config/application.yml`：

```yaml
qa:
  ocr:
    python: <装着依赖的那个解释器的绝对路径>
```

字段说明见仓库里的 `config/application.yml.example`。这个文件含本机绝对路径，
**不要提交到仓库**（`.gitignore` 已忽略）。

**② 想强制关掉 GPU**：配置里把 `qa.ocr.use-gpu` 设成 `off`。

#### 关于本机模型与 OCR 的关系

GPU 加速只影响 OCR。本地模式的对话模型走 Ollama，显存由 `qa.local.num-ctx` 控制
（默认 `auto`，按时显存自动选 4096 / 8192 / 16384）。

## 两种运行模式

由环境变量 `QA_PROFILES` 控制（默认 `h2,local`）：

| 组合 | 含义 |
|---|---|
| `h2,local` | **默认**：零安装 + 本地模型，完全离线 |
| `mysql,local` | 用本机 MySQL 存元数据 |
| `h2,cloud` | 本地库 + 云端模型（无显卡的机器走这条） |

>  `QA_PROFILES` **只管数据源**。模型用本地还是云端由 `qa.mode` 决定，
> 且可以在界面上运行时切换（重启后回到 `qa.mode` 的值）。

云端模式需要API Key，写进项目根目录的 `.env`（**不要**写进配置文件，见下方"授权与合规"）：

```bash
set QA_PROFILES=h2,local
set QA_MODE=cloud
set DEEPSEEK_API_KEY=sk-xxx        # 对话
set DASHSCOPE_API_KEY=sk-xxx       # 向量（阿里云百炼）
```

> **两个 Key 都要填。** 只填对话 Key 的症状很有迷惑性：**能聊天，但一上传文件就"解析失败"** ——
> 解析本身没问题，卡在分块之后的 embedding，那一步失败整条入库都会失败。
> 向量也可以换成硅基流动（`qa.cloud.embedding.provider: siliconflow`，2560 维，
> 与本地同源、切换免重建索引），但**前提是那台机器能访问 `api.siliconflow.cn`**：
> 有网络（校园网 / 公司内网 / 带 TLS 拦截的出口）会在握手阶段被掐断，
> 报 `SSLHandshakeException`，换 Key 解决不了，只能换厂商或改用本地模型。

`.env` 已被 `.gitignore` 排除，**永远不会被提交**。界面上只显示"已配置 / 未配置"，
不回显内容；`/api/v1/system/status` 也只回**末四位掩码**（如 `***c747`），
用于核对"现在用的是哪一把 Key"。

## 特性

- **三层记忆体系**
  - L1 上下文窗口：按 token 分配预算，不让检索片段被挤掉
  - L2 会话记忆：同一会话内的多轮连贯，**落库，重启不丢**（切模型、刷新页面也接得上）
  - L3 长期记忆：跨会话记住你的偏好与事实，**看得见、改得掉、一键清空**
- **回答必须有依据**：知识库问题只使用检索到的原文，并给出引用来源；
  **本单位的细节**（规定、流程、时限、名单、联系方式）资料里没有就明确说"未找到"，禁止编造
- **知识库以外的问题也能问**：常识、通用知识、算数、闲聊这类问题会**正常回答**，
  但回答开头会标明"以下内容不来自知识库，仅供参考"——这样"哪句有出处、哪句没有"始终分得清。
  混合问题（既问概念又问本单位规定）会分成两段处理
- **引用来源**：每条回答标注来自哪个文档的哪一段，可核对；默认折叠，不挤占正文
- **文档格式**：txt / md / docx / **doc** / pdf / xlsx / html，**以及图片 jpg / jpeg / png / webp / bmp**
  （`.doc` 是 Word 97-2003 老式二进制；已用真实文件实测通过，但复杂排版仍**建议优先用 .docx**）
- **扫描版 PDF 与图片可识别**：**上传后自动识别一次**（本机离线 OCR，RapidOCR + ONNX，不联网），
  状态变「待确认」，你核对后点确认才入库。图片与扫描件同类 —— 都没有文字层，走同一条路
- **本地与云端可运行时切换**（对话模型立即生效；向量模型需重启并重建索引）
- **思考模式可运行时开关**：开＝更准（首字多约 1 秒），关＝更快。实测见设计文档
- **故障有话说**：连不上 / Key 无效 / 余额不足 / 被限流 / 模型名写错 …… 每种都告诉你**该做什么**
- **元问题与冒烟口令**：问"你是谁""你是什么模型""测试"直接给固定回复，不依赖模型

## 支持的模型厂商

本地模式用 Ollama；云端模式内置 **10 家**预设。换厂商只需改 `qa.cloud.chat.provider` /
`qa.cloud.embedding.provider`，再把对应 Key 填进 `.env`。

| 厂商 | provider | 对话 | 向量        | 注意事项 |
|---|---|----|-----------|---|
| DeepSeek（深度求索） | `deepseek` | 支持 | 不支持       | 无 embedding 接口；`deepseek-chat` / `deepseek-reasoner` 已停用，现役 `deepseek-flash` |
| 阿里云百炼 | `dashscope` | 支持 | 支持 1024 维 | **默认向量源**（可达性最稳）；Key 与地域绑定，跨地域报 401；单次最多 10 条 |
| 硅基流动 | `siliconflow` | 支持 | 支持 2560 维 | 官方未标注默认维度，必须显式配 `dimension`；⚠️ 部分网络访问 `api.siliconflow.cn` 会在 TLS 握手阶段被掐断（报 `SSLHandshakeException`），换 Key 无效 |
| 智谱 BigModel（GLM） | `zhipu` | 支持 | 支持 2048 维 | base-url 是 `/api/paas/v4`，**不是** `/v1` |
| 月之暗面 Kimi | `kimi` | 支持 | 不支持       | 无 embedding；`moonshot-v1-*` 已下线 |
| 火山方舟（豆包） | `ark` | 支持 | 不支持       | embedding **不走 OpenAI 协议**，必须用方舟 SDK |
| 腾讯混元 | `hunyuan` | 支持 | 支持 固定 1024 | 不要传 `dimensions`；`stop` 语义与 OpenAI 相反 |
| MiniMax | `minimax` | 支持 | 不支持       | 部分 OpenAI 参数被忽略；`n` 只能为 1 |
| 阶跃星辰 StepFun | `stepfun` | 支持 | 不支持       | 无 embedding |
| 百度千帆 v2 | `qianfan` | 支持 | 支持 维度固定    | 鉴权是 Bearer，**不是** AK/SK 签名 |

>  **五家不能作向量源**（DeepSeek / Kimi / 方舟 / MiniMax / 阶跃）：它们的向量接口要么不存在、
> 要么不走 OpenAI 协议。配成向量源必然失败 —— 界面上会直接标红，别绕过去。
>
> 完整清单（各家可用模型名、向量维度、注意事项）在界面上：
> **系统状态 → 内置厂商**，并且能看到 Key 配没配。

## 从源码构建

```bash
git clone <repo-url>
cd qa-assistant

# 1) 前端（仓库里已含构建产物，只在改前端时需要重新执行）
cd web && pnpm install && pnpm build && cd ..

# 2) 后端
mvn clean package

# 3) 运行
java -jar target/qa-assistant-1.0.0-SNAPSHOT.jar
```

> **顺序不能反**：Vite 的产物输出到 `src/main/resources/static/`，
> 必须先构建前端再 `mvn package`，否则打进 jar 的还是上一次的界面 ——
> 表现为"我明明改了前端，运行起来却没变化"。
> 更隐蔽的一种：`target/classes` 里的 `index.html` 与 `assets/` 名字对不上，
> 打开页面**一片空白**且控制台 404。`start.cmd` / `start.sh` 会检查 jar 里有没有前端来提前拦住它。

**前端开发模式**（改代码即时热更新，不必反复打包）：

```bash
# 终端 1：后端
mvn spring-boot:run

# 终端 2：前端（访问 http://localhost:5173，/api 会代理到 8080）
cd web && pnpm dev
```

**出发布包**：

```bash
package-release.cmd            # Windows
./package-release.sh           # Linux / macOS
# 产物：release/qa-assistant-1.0.0.zip + qa-assistant-1.0.0.zip.sha256
```

## 常见问题

| 问题 | 原因与处理                                                                                                                                                                     |
|---|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 启动报 `UnsupportedClassVersionError` | JDK 版本低于 17。`java -version` 确认；`start.cmd` 会在启动前拦住                                                                                                                        |
| 页面一片空白 / 控制台 404 | jar 里没有前端产物，或 `index.html` 与 `assets/` 名字对不上。重新 `cd web && pnpm build` 再 `mvn clean package`                                                                              |
| 回答很慢、每个问题先"思考"十几秒 | 对话模型误用了推理模型。请用对话模型如：`qwen3.5:9b`，**不要**用推理模型如：`deepseek-r1:8b`                                                                                                            |
| 每个问题都要等 7~10 秒，日志里 `load_duration` 一直是好几秒 | 两个模型在显存里互相挤：多半是漏了快速开始的第 2 步。执行 `ollama create qa-embed:4b -f deploy/ollama/Modelfile.qa-embed`，并把 `qa.local.embedding-model` 设为 `qa-embed:4b`。用 `ollama ps` 可确认两个模型是否同时在列 |
| 闲置一会儿后，第一个问题又变慢（之后恢复） | 正常现象：Ollama 默认闲置 5 分钟就卸载模型，下一问要重新载入显存（实测第 1 问约 7.9 s、第 2 问约 3.0 s，之后回到 1 秒内）。想避免可给 Ollama 设 `OLLAMA_KEEP_ALIVE=30m`（或 `-1` 永不卸载，代价是显存长期被占）                                |
| 提问后长时间无响应或显存溢出 | 显存不足。把 `qa.local.num-ctx` 显式降到 `8192`，或改走云端模式                                                                                                                             |
| 回答偶尔"资料里明明有却说找不到" | 点「系统状态」看**思考模式**是否被关了。实测关掉思考会把资料里确实存在的答案答成"未找到"（本地/云端模型差异见设计文档 7. 关键实测数据）；把开关打开即可                                                                                         |
| 提示"模型服务拒绝了当前 API Key（401）" | Key 不对/过期，或与端点地域不匹配（百炼的 Key 与地域绑定）。改 `.env` 后**必须重启应用**，再到「系统状态」点自检确认                                                                                                     |
| 提示"云端账户余额不足或额度已用尽（402）" | 去厂商控制台充值，或先在「模型来源」里切回本地模型                                                                                                                                                 |
| **能聊天，但一上传文件就"解析失败"** | 十有八九是**向量那侧的 Key 没配或连不上**：解析、分块都正常，卡在分块之后的 embedding，那一步失败整条入库都会失败。先看"失败原因"那一列 —— 提示缺 Key 就去 `.env` 补齐（默认组合要 `DEEPSEEK_API_KEY` + `DASHSCOPE_API_KEY` 两把），提示 `SSLHandshakeException` 见下一条 |
| 失败原因里写着 `javax.net.ssl.SSLHandshakeException: The remote host closed the handshake` | **不是 Key 的问题**（Key 不存在报"缺少…"、Key 错了报 401，各有各的文案），而是 **TLS 握手被中间网络掐断** —— 常见于校园网、公司内网、带 HTTPS 拦截代理的出口，自己改不了。换 Key、重填 `.env` 都不会有任何改善。两条出路：① **换一家向量厂商**（默认已是可达性最稳的百炼；若你手动改成了硅基流动，改回 `qa.cloud.embedding.provider: dashscope` 即可，**换完必须重建索引**）；② **改用本地模型**（`QA_MODE=local`，完全不联网） |
| 上传的扫描版 PDF 检索不到内容 | 先看状态标签：显示**「待确认」**说明本机已自动识别好了，点「查看识别结果」核对后确认入库即可。显示**「失败」**才需要处理 —— 看"失败原因"那一列写的是什么（多半是没装 OCR 依赖，四步安装见上方「扫描版 PDF 与图片的文字识别」） |
| 回答里混进了知识库没有的内容（尤其是数字、版本号） | **已知短板，且提示词拦不住**。当检索到的片段"话题相关、但恰好不含那个具体事实"时，模型会用自己的训练知识补上，还标着出处。实测：资料里有答案的提问 8/8 全对、资料完全没这话题 6/6 如实说"未找到"，只有这中间地带会编。**处理**：点开「引用来源」核对原文；涉及数字/编号/版本的结论务必核对。想减少诱因可把 `qa.retrieval.top-k` 降到 4、`qa.retrieval.min-score` 提到 0.80+（代价是可能漏掉本该命中的片段） |
| 删掉了记忆，回答还是老样子 | **删除只清掉"跨会话记住的偏好"，清不掉当前会话里已经形成的习惯。**同一条会话中模型已经按那个偏好回答过多轮，它会继续延续（那是对话历史，不是记忆）。系统的处理：删除后会提示模型别再沿用，并有规则保证**从下一轮起回到默认风格**（实测 10/10 生效）。想彻底干净就**开一个新会话**——新会话不带旧历史，行为一定回到默认 |
| 小文档（几页的扫描件、单张图片）检索不到 | **已知短板**。相似度分数跟知识库规模强相关：几百块的库 0.80~0.85，只有一两块的小文档 0.67~0.78。默认阈值已按此降到 0.65（否则这类文档会"入库成功却永远答未找到"）。若你的库以短文档为主，可把配置里的 `qa.retrieval.min-score` 再降到 0.60 |
| 重启后知识库空了 | 检查 `%USERPROFILE%\.qa-assistant\index\` 是否存在且可写                                                                                                                           |
| 改了 `.env` 但界面显示还是旧值 | 配置只在**启动时**读取，改完要重启应用；页面每 30 秒会检测到后端配置变化并提示你刷新                                                                                                                            |
| `start.cmd` 双击后一堆"不是内部或外部命令" | 该文件被编辑器改存成了 UTF-8。见下方"贡献与约定"                                                                                                                                              |

## 贡献与约定

- **`start.cmd` 必须以 GBK(936) 保存。** cmd.exe 按系统 ANSI 代码页解析 `.cmd`，
  存成 UTF-8 会让中文注释变成乱码命令并直接报错；同理**不要**在脚本里 `chcp 65001`。
  编辑后请确认文件仍是 GBK，否则 Windows 用户双击即报错。
- **`start.sh` 必须是 LF 换行**（`.gitattributes` 已声明）。
- 提交前请确认**没有把 `.env` 或任何真实 Key 带进仓库**（`.gitignore` 已排除，但别用 `git add -f`）。
- 代码注释用中文、标识符用英文；改行为时**同步改 `docs/DESIGN.md` 对应章节**。
